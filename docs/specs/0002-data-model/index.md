## Summary

This spec settles what tracepath stores: the things it pulls out of JobHunt's decision records, the links between them, and the shape they take in Neo4j. There are three kinds of node. A **Record** is a whole document (a spec's `index.md`, the scope document, or one feature row inside it), created by code from the file tree. An **Entity** is one extracted item (an acceptance criterion, a constraint, a consequence, a follow up item, a build step, a test scenario, a capability, or `unclassified` when it fits none of those), extracted by the model. An **Unresolved** node stands in for a reference the code could not name, so a chain shows the gap instead of guessing. Links between them are typed (superseded by, corrected by, amended by, blocked by, verifies, satisfies) with `UNCLASSIFIED` as a real value that keeps the connecting words from the page. Two different kinds of doubt stay separate and visible: "I do not know what kind of thing this is" (an `unclassified` entity) and "I do not know which thing this points at" (an `Unresolved` node).

## Requirements

**User stories**:

- As the author, I want every item a chain passes through to keep its own citation (file, section, line, commit), so an answer can be checked against the record it came from.
- As the author, I want a reference the tool cannot resolve to appear in the chain as unresolved, so a chain never breaks quietly and never invents a target.
- As the author, I want a real link that fits none of the named types to be stored with the words that made it, so nothing is forced into the nearest type and nothing is dropped.
- As the author, I want the schema to survive the corpus as it really is (letter suffixed ids, struck text, revision notes above the first heading, references to scope features), so the first real extraction does not force a redesign.

**Acceptance criteria** (the contract, each criterion is independently checkable):

- **AC-1**: One set of frozen Pydantic models is the whole schema. It holds three closed enums: entity type (`Feature`, `Constraint`, `AcceptanceCriterion`, `Consequence`, `FollowUp`, `BuildStep`, `TestScenario`, `unclassified`), relationship type (`superseded-by`, `corrected-by`, `amended-by`, `blocked-by`, `verifies`, `satisfies`, `unclassified`), and the seven known trap flags. `model_json_schema()` is the only schema handed to the model call and the only one validation uses, so no second schema exists to drift.
- **AC-2**: An extraction unit is one of: a top level `##` section of a spec's `index.md`; the text above the first `##` in that file (the `Preamble` unit); one `### N.` feature row of `docs/scope/scope.md`; the text above the first `### N.` row inside a `##` section of that file (the `Intro` unit, which 5 of its sections carry: Slice 1, Slice 2, v1 extras, v1.5 and v2; Foundation has none); or one other `##` section of `docs/scope/scope.md`. Every byte of those files belongs to exactly one unit, so nothing is skipped without a record of it. · **Amended 2026-09-23**: the `Preamble` unit is **the text above the first `##` of either file kind**, a spec's `index.md` or `docs/scope/scope.md`, not of a spec's `index.md` alone. As first written this criterion contradicted its own byte coverage rule: 1,233 characters at the head of the scope document, its title and the paragraph naming what JobHunt is, belonged to no unit at all. The behaviour was already correct in the build and is pinned by `test_the_scope_head_above_the_first_heading_is_a_preamble` and `test_every_spec_starts_with_a_preamble_then_only_sections` in `tests/test_extract_units.py`; this is the criterion catching up to the code, so no build step follows from it.
- **AC-3**: Only a token matching `AC-<digits><optional single lowercase letter>` is a verbatim id. Code qualifies it as `<record>/<id>` (`0008/AC-10b`). Every other entity gets a derived id `<record>#<section-slug>:<n>`; a section slug that repeats inside one record gets a numeric suffix. `n` follows each span's located start offset in the unit's source text, so `locate_line()` runs before `assign_ids()`. A span that cannot be located keeps the model's own output order, behind the located ones. **That fallback is not a stability guarantee**: an unlocatable span can take a different `n` in a different run, which is safe only because `compare_runs()` (AC-11) collapses every derived id to `<derived>` before comparing. The model writes only `derived:N` placeholders and never a slug, a qualified id, or a spec number.
- **AC-4**: Every entity carries its citation: file path, section heading, corpus commit, and `line`. `line` is located by code: the definition line for a verbatim id, otherwise the best deterministic text alignment above a stated threshold. Below that threshold `line` is `null`. It is never guessed and never approximated silently.
- **AC-5**: A deterministic pre-check, run before the model call, reports the character ranges of every `~~struck~~` span in a unit. An entity whose span falls inside a struck range is stored with `struck` true. Where one verbatim id carries both struck and unstruck text, the unstruck text keeps the verbatim id and the struck version takes a derived id. Whether something is struck never depends on the model noticing it.
- **AC-6**: A follow up item's checkbox (`- [x]` or `- [ ]`) is read by the same pre-check into `followup_status` (`done` or `open`), not by the model.
- **AC-7**: A relationship endpoint is either a local placeholder id (an entity in the same output) or a structured reference `{record, id, mention}`, where `mention` is the verbatim connecting text. Code resolves references after the whole corpus is loaded: `record` plus `id` becomes `<record>/<id>`, `record` alone becomes that Record, and anything that resolves to nothing becomes an `:Unresolved` node carrying `mention`. No relationship is dropped for having an endpoint that cannot be named. · **Amended 2026-09-23**: this criterion governs **resolution, what an endpoint becomes when the corpus cannot name it. It is not a promise that every extracted link reaches the graph regardless of whether its parts passed review**; that question is acceptance, and AC-11 settles it. The distinction is not academic. The first full load failed on `UNCLASSIFIED links: asked to write 7 but the database wrote 2`, from 14 endpoints naming entities that had been routed to review and so were never written. The counter assertion of AC-13 did its job exactly, failing loudly with zero phantom nodes, but the two criteria had no stated boundary between them. "Cannot be named" means the corpus holds no such thing. An entity that exists and was held back is named perfectly well, so it never reaches the `:Unresolved` fallback.
- **AC-8**: Every history link is stored old to new: `(old)-[:SUPERSEDED_BY|:CORRECTED_BY|:AMENDED_BY]->(new)`. Finding the current version is always "follow outgoing history links until there are none".
- **AC-9**: The graph has one uniqueness constraint per node kind: `:Entity(canonical_id)`, `:Record(canonical_id)`, `:Unresolved(canonical_id)`. Every entity carries `:Entity` plus exactly one type label. Every entity is `PART_OF` exactly one Record. A `scope_feature` Record links `SPECIFIED_BY` to zero or more spec Records, read from its pointer line.
- **AC-10**: Both "not confident" values exist and are distinct in the stored graph. An entity whose kind fits none of the named types is typed `unclassified` and carries `unclassified_note`. A reference whose target cannot be named becomes an `:Unresolved` node holding the verbatim mention and its source record. A link whose type fits none of the named types is stored as `UNCLASSIFIED` with its verbatim `phrase`. None of the three is dropped, and none stands in for either of the others.
- **AC-11**: `compare_runs()` decides agreement on a stated signature and nothing else: per entity, the tuple (canonical id with every derived id collapsed to `<derived>`, type, sorted flags); per relationship, the tuple (type, from, to, same collapsing). Span text, rationale spans, citations and provenance are ignored, as the tested comparator ignores them; `struck` and `followup_status` are excluded because code sets them identically for all three runs. An item routes to review when the three runs disagree on that signature, when any known trap flag is present, or when the entity's type is `unclassified`. An `UNCLASSIFIED` relationship alone does not route to review; it enters the graph carrying its phrase, visible in the chain. Only accepted items are written to the graph. · **Amended 2026-09-23**, four changes. The first three came from the first real extraction runs; **(d)** came later the same day from measurement over the committed artifacts, and closes a hole the first three left open.

  **(a) Flags leave the signature, and a derived entity is identified by its located line.** The signature is now, per entity, the tuple (a verbatim canonical id as it stands, else the entity's located `line`, else `<derived>` when that line is null, plus type), and per relationship (type, from, to, same rule on each endpoint). Sorted flags are removed from both. The located line fixes that at no cost, because `locate_line()` already computes it and every entity already stores it (AC-4), and it does not reopen what the collapse guards against: AC-3 collapses derived ids because **the ordinal `n`** shifts between runs when the runs find different numbers of spans. A line is a property of the source text, not of the run, so it does not shift. Flags remain a review trigger in their own right, unchanged, which is the point: this criterion already routes any item carrying a known trap flag to review, so keeping flags in the signature counted them twice. The second count only ever harmed **other** items, marking unflagged entities as disagreements because a flag moved on a neighbour. Measured: flags are the least stable thing the model produces, 11 / 12 / 11 per run at default effort against 4 / 4 / 8 at `medium` on the same section, while the type counts over the same runs stay near identical. Agreement was largely measuring flagging volume.   **(b) The comparison counts items rather than setting them.** `compare_runs()` compares each run's signatures as a **multiset**, not a set. A signature must appear the same number of times in all three runs to be shared, and where the count differs, **every copy of that signature routes to review, not only the surplus**. Accepting the first `min(counts)` copies and holding the rest would assert an identity the runs never established: if one run finds four claims sharing a signature and another finds two, nothing says which two correspond, and picking by position would be inventing that correspondence. `RunComparison` therefore carries counts rather than sets: shared is the signatures whose count is identical in all three runs, differing is everything else, and the queue orders held copies by lowest located offset so the ordering is deterministic and readable rather than arbitrary. This is not optional alongside (a): removing flags shortens the signature, so more entities collapse onto the same one, and under set comparison that makes acceptance **less** safe rather than more. On 0012 `Consequences` at `medium` (15 / 16 / 15 entities, nearly all `Consequence` with derived ids) the shortened signature under set comparison would read as agreement, and all 15 of the first run's entities would be accepted while a sixteenth that two runs never found went unnoticed. Counting makes 15 against 16 a disagreement, which is what it is.

  **(c) A link whose endpoint was not accepted is held, not written.** A relationship is accepted only when every endpoint it needs is itself accepted, or is a `:Record` (always written, since code creates them), or is genuinely unresolvable under AC-7. An endpoint naming an entity that exists but was routed to review makes the relationship route to review too, under its own reason `endpoint_not_accepted`, naming the entity it waits on. Accepting that entity in review brings its held links with it. The other two readings were both rejected, and for reasons this spec already states. Turning the endpoint into an `:Unresolved` node breaks AC-10 and key invariant 8, because the target is named and what is actually uncertain is whether the extraction is trustworthy: it would draw a gap in the chain that does not exist, which is worse than a missing link, since a reader gets a wrong story rather than no story. Writing the unaccepted entity so its link has somewhere to land voids this criterion's own last sentence and lets an item the three runs disagreed about into the graph through a side door, with no ruling behind it and no honest value for `accepted_by`. **A held link is not a dropped link**: it sits in `artifacts/review-queue.json`, which is tracked in git (spec 0001), beside the entity it depends on. This rule is enforced in routing, before anything is written, so the run artifact records the decision and the counter assertions of AC-13 hold by construction rather than by luck.

  The contract between routing and resolution is stated, because leaving it implied is how the first load failed. **Routing runs first and removes every held relationship**, so `resolve_endpoints()` never receives one, and its `known_entities` set is **the accepted entities only**. Holding is therefore decided before resolution, never inside it, and the `:Unresolved` fallback keeps meaning exactly what AC-7 says it means. A reference naming a `:Record` that the corpus does not hold is **not** a held case: no such record exists to wait on, so it takes the `:Unresolved` fallback like any other unnameable target. Only an entity can be held, because only an entity can be routed to review.

  One requirement this places on a step that does not exist yet: **the review step must bring an entity's held links with it when the entity is accepted**, or a held link would sit in the queue forever with nothing to trigger it. No review workflow is designed in this spec or in spec 0001, and this does not design one. It records the requirement so that whoever designs it is not free to ignore it, and so that a reader does not mistake the sentence above for a mechanism that already exists.

  **(d) A derived entity whose `line` is null routes to review, under the reason `span_not_located`. Added 2026-09-23**, from measurement over the committed artifacts. Amendment (a) identifies a derived entity by its located line, and states plainly what that line is for: without it the tuple is (`<derived>`, type), "so every derived entity of one type in a unit would share one signature and agreement would test only how many items of that type each run found, never whether two runs found the **same** one.   **It applies to a derived entity only, and a verbatim one is deliberately exempt.** The rule is about identity, not about citations. `entity_identity()` returns a verbatim canonical id as it stands, whatever its `line`, so an `AC-N` entity whose definition line was not found still has a stable identity that all three runs compare on, and nothing about it is ambiguous. This is currently true because two independently motivated rules happen to compose, so it is recorded here as a property to preserve, not an accident to rely on quietly.

  `span_not_located` carries no payload, like the other three within unit reasons. It is not a fifth home for uncertainty and does not touch key invariant 8: a held item is absent from the graph, and this reason changes only why one is held.

## Decision

**Chosen option**: Option 1: One extraction schema, three node kinds, deterministic markers in code

Store each extracted item as an `:Entity` node carrying one type label and its own citation, group items under code created `:Record` nodes for the documents they came from, and keep every reference the code cannot name as an `:Unresolved` node so unresolved identity is a value in the graph rather than a dropped link.

## Feature design

**Data model sketch**

`:Record`, one per document, created by code, never by the model.

| Property | Type | Required | Notes |
|---|---|---|---|
| `canonical_id` | str | yes | `0012` for a spec, `scope` for the scope document, `feature-21` for a feature row. Unique across all Records. |
| `kind` | str | yes | One of `spec`, `scope_document`, `scope_feature`. New kinds (a `rationale` document) are added here without touching existing nodes. |
| `title` | str | yes | The document's own heading text. |
| `status` | str \| null | no | Parsed from `**Status**:` for a spec, from the row heading for a feature row (`done`, `needs a decision`). |
| `path` | str | yes | Repository relative path inside the snapshot. |
| `commit` | str | yes | The pinned corpus commit, `2e40bcf`. |
| `aliases` | list[str] | yes | Every name the corpus uses for this record: the number, the title, the directory slug, and for a feature row the `feature N` form. This is what carries "the same thing named several ways" until name resolution (feature 7) does the matching. |

`:Entity`, one per extracted item, always carrying `:Entity` plus one type label.

| Property | Type | Required | Notes |
|---|---|---|---|
| `canonical_id` | str | yes | `0008/AC-10b` (verbatim) or `0012#build-plan:2` (derived). Unique across all entities. |
| `type` | enum | yes | `Feature`, `Constraint`, `AcceptanceCriterion`, `Consequence`, `FollowUp`, `BuildStep`, `TestScenario`, `unclassified`. Also the node's second label. |
| `text` | str | yes | The span the model kept. |
| `rationale` | list[str] | yes | The spans the deletion trick removed, kept because they are the "because" text a why answer shows. Empty list when there are none. |
| `flags` | list[str] | yes | Known trap flags from the closed set of seven, carried over unchanged from the tested pipeline: `rationale_boundary_call` (was a clause rationale to drop or load bearing to keep), `multi_condition_split` (was a multi condition sentence one item or several), `implicit_feature_inferred` (a capability inferred from implication, not an announcing sentence), `embedded_second_claim` (a clause that looked like rationale but hid its own testable claim), `relationship_type_ambiguous` (which link type applied was not obvious), `entity_type_ambiguous` (the item fits no named type and went to `unclassified`; only ever set on an `unclassified` entity), `granularity_boundary_call` (choosing between named types was a close call). Empty list when there are none. |
| `unclassified_note` | str \| null | no | Required when `type` is `unclassified`, null otherwise. |
| `id_source` | str | yes | `verbatim` or `derived`. |
| `label` | str \| null | no | The author's own label for an unnumbered item (`binding rule 6`, `key invariant 1`), verbatim. Name resolution reads this. |
| `struck` | bool | yes | Set from the pre-check's character ranges (AC-5), never by the model. |
| `followup_status` | str \| null | no | `open` or `done` for a `FollowUp`, null otherwise. Parsed from the checkbox. |
| `file`, `section`, `line`, `commit` | str, str, int \| null, str | yes except `line` | The citation. `line` is null when it cannot be located (AC-4). |
| `model`, `prompt_version`, `extracted_at`, `accepted_by` | str, str, str, str | yes | Provenance. `accepted_by` is `auto` or `review`. |

`:Unresolved`, one per reference the code could not name.

| Property | Type | Required | Notes |
|---|---|---|---|
| `canonical_id` | str | yes | `unresolved:<source record>:<slug of mention>`. Scoped to the source record on purpose: the same words can mean different things in different documents. |
| `mention` | str | yes | The verbatim reference text (`binding rule 6`). |
| `source_record` | str | yes | The record whose text made the reference. |
| `file`, `section`, `line` | str, str, int \| null | yes except `line` | Where the reference was written. |

**Relationships**

| Type | From → To | Cardinality | Properties |
|---|---|---|---|
| `PART_OF` | Entity → Record, and scope_feature Record → scope_document Record | N:1 | none |
| `SPECIFIED_BY` | Record (`scope_feature`) → Record (`spec`) | 1:N, and absent when the row cites no spec | `source_line` |
| `SUPERSEDED_BY` | old → new | N:M | `phrase`, `date`, `flags`, citation |
| `CORRECTED_BY` | old → new | N:M | same |
| `AMENDED_BY` | amended → amending | N:M | same |
| `BLOCKED_BY` | blocked → blocker | N:M | same |
| `VERIFIES` | TestScenario → AcceptanceCriterion | N:M | same |
| `SATISFIES` | BuildStep → AcceptanceCriterion | N:M | same |
| `UNCLASSIFIED` | as the text reads | N:M | same, and `phrase` is required |

Every relationship endpoint may be an Entity, a Record, or an Unresolved node. History links always point old to new (AC-8).

The other three (`runs_disagree`, `known_trap_flag`, `unclassified_type`) carry no payload. **Amended 2026-09-23**: a fourth payload free reason joins them, `span_not_located`, for a derived entity whose `line` is null (AC-11d). |
| `model`, `queued_at` | str, str | yes | Provenance, as the run artifact records it. |

Rows are ordered by lowest located offset within a unit, so the queue reads in document order and two runs of the same extraction produce the same file. · **Clarified 2026-09-23**: that describes the **located** rows. A row with no offset, which is every relationship and every unlocatable span, sorts behind all located rows, then by signature, then by the order routing produced it. That tail is fully deterministic, so the file is still byte stable from one rebuild to the next, but it is **not** in document order, because there is no document position to order it by. AC-11(d) makes that tail larger, so the distinction is worth stating rather than leaving a reader to infer that every row reads in source order.

**State transitions**

An entity has no lifecycle of its own; the graph is rebuilt from the JSON run artifacts (spec 0001). The one ordered thing is the pipeline: `unit → pre-check → three model runs → validate → compare → assign ids → accepted or review → load`. Only accepted items reach the graph.

**Key invariants**

1. `canonical_id` is unique across every entity, enforced by Neo4j, not by the loader.
2. Every entity belongs to exactly one Record, and that Record exists before the entity is written.
3. The model never writes a final id and never writes a qualified one. Code owns identity.
4. `struck` and `followup_status` come from deterministic parsing only.
5. A reference that cannot be named becomes a node, never a dropped link and never a guessed target.
6. A relationship whose type fits none of the named types keeps the words that made it.
7. History links point old to new, without exception.
8. Uncertainty has three separate homes: `unclassified` type (kind unknown), `:Unresolved` node (identity unknown), `UNCLASSIFIED` link (link kind unknown). None is a substitute for another. · **Amended 2026-09-23**: being held for review is not a fourth home and must never be expressed as one. A held item is not uncertain in the graph, it is **absent** from the graph, waiting on a person. Writing an `:Unresolved` node because an entity was held would break this invariant in the direction it was written to prevent.
9. Nothing under `src/` or `tests/` reads `reference/`.

**Security model**

No new surface. One local user, a local Neo4j in Docker, a read only corpus snapshot, and the Anthropic key already governed by spec 0001. The corpus is public project documentation, so no personal data enters the graph.

**Configuration required**

None beyond spec 0001's `.env` (`NEO4J_*`, the Anthropic key).

## Consequences

**Positive**:

- Uncertainty is visible in three separate, queryable forms rather than collapsed into one word, which is what the scope asked for and what keeps a chain honest.
- Identity stays in code. The model never writes an id, so two runs of the same section produce the same ids and the run comparator keeps working.
- The named template types keep `unclassified` rare. Under HANDOFF's rules about 837 items (roughly 280 consequences, 185 follow ups, 206 build steps, 166 test scenarios) would have been unclassified and all routed to review, against 325 acceptance criteria.
- New record kinds (rationale documents) and new entity types (an Alternative) are additive: a new `kind` value or enum value, with no restructuring of existing nodes.
- Citations carry a line, so a chain link lands where the eval's own traces land.

**Negative / tradeoffs**:

- Extraction stays limited to `index.md`, the preamble and the scope document. "Why not X" questions are therefore unanswerable, and that is not a small corner: in a census of 20 self picked questions across four specs, 9 needed `rationale.md`, and every one of them asked about a rejected alternative. Correction narratives that live only in `rationale.md` are invisible too.
- Worse than silence: an `index.md` can state a reason its own `rationale.md` calls false. Spec 0014's index line 68 lists `redirect` among the triggers that re-render `/search`; its rationale line 102 says that is exactly the wrong reason, because `redirect()` streams the destination instead. With `rationale.md` out of scope, tracepath can present that reason as current with nothing contradicting it.
- Four new entity types reverse a rule the tested prompt states plainly (`solutions.xml` line 32: "Consequences and Follow-up items are not requirements: use unclassified"). The tested few shot examples do not cover them, so AC-14's run is a real gate, not a formality.
- A `Feature` entity (a capability claim written inside a record) is never linked to the `scope_feature` Record covering the same capability, unless the text names the row. Matching them is deferred to name resolution (feature 7); until then the two live side by side unconnected.
- Neo4j Community enforces only uniqueness. Required properties, property types and composite keys are all Enterprise features, so every other guarantee rests on the loader's own assertions.
- `line` is best effort by design. A span is not a verbatim substring of the source (the model drops rationale clauses mid sentence), so some citations will carry `null`.
- **Added 2026-09-23, a known failure mode: extraction can keep a struck claim and lose its replacement.** Where one bullet holds a struck claim and the correction that replaces it, the model sometimes returns a single span covering both. The span begins inside the `~~…~~` range, so AC-5's deterministic rule correctly marks the entity `struck`, and the effect is that **the current fact is stored and labelled obsolete**. That is worse than losing it outright: a chain asking what is current finds the replacement filed as superseded text. Measured on bullet 3 of 0012 `## Consequences` at both effort levels, three runs each: at `medium` 1 of 3 runs dropped the replacement, at `low` 2 of 3 merged it into a span marked `struck=True`. The two failures differ in direction, `medium` losing the correction and `low` mislabelling it, and the direction is why effort is `medium` (spec 0001's run policy row). This is a model behaviour, not a pre-check bug: the pre-check is right about the character ranges every time, and code cannot tell a merged span from a correct one. **The review queue caught every instance, in both settings, only because the runs disagreed.** Nothing about this is guaranteed. Three runs that agreed on a merged span would accept it, and the graph would then assert the replaced fact as history and hold no current version of it at all. Feature 8's `Done when` says a replaced fact must never come back as current; this is its mirror image, the replacement never coming back. Spans for all six runs: `experiments/0002-effort-low-fidelity/data/bullet-split-comparison.json`.
- **Added 2026-09-23**: counting signatures rather than setting them (AC-11b) makes the heterogeneous units disagree **more** often, not less. The widest entity count spreads measured so far are exactly there: 0008 `Preamble` at 16 / 17 / 27, the `feature-21` scope row at 15 / 38 / 14, and `## Feature design` is the largest and most varied unit kind in the corpus (mean 15,407 characters against `## Consequences` at 3,886, maximum 38,663), so expect it to behave the same way. That is the criterion becoming honest about variance it was previously blind to, not a regression. It should not be "fixed" by returning to set comparison; a set comparison hides the surplus rather than resolving it.
- **Added 2026-09-23**: a signature whose count differs across runs sends **every** copy to review, not only the surplus (AC-11b), so a dense bullet that splits into several same line claims routes wholesale until a person rules on it. Bullet 9 of 0012 `## Consequences` is the worked example: `medium` produced 5 / 5 / 4 entities from one bullet, so all of them would be held. That is the intended direction rather than a cost to be engineered away, because AC-11's promise is that only what all three runs agreed on is written, and no rule can say which four of one run's five claims correspond to another run's four.
- **Added 2026-09-23**: identifying a derived entity by its located line (AC-11a) fails in the safe direction, and the failure will be visible. Where two runs locate the same claim at slightly different lines, because one span starts before an inline label and the other after it, the signatures differ and the item routes to review rather than being accepted. **Those queue entries are not extraction defects and should not be read as such.** Say it plainly, because the natural response to a queue full of near duplicates is to loosen the comparison, which is the one change that would put unverified items into the graph.
- **Added 2026-09-23**: `line` is a discriminator, not a unique key, so it is worth stating what agreement does and does not prove. ~~It is null below AC-4's alignment threshold, measured at 99.4% located over the pinned snapshot, so roughly 1 span in 170 still collapses to `<derived>` and for those the old type only weakness remains.~~ Several claims split from one dense bullet can also share a line. In both cases agreement proves that all three runs found the same **number** of items of that type at that place, not that they found the same items. Where the line differs, agreement does prove the runs are talking about the same place in the source. · **Corrected 2026-09-23 by measurement over the committed artifacts. The struck sentence was wrong by a factor of ten, and the error was one of kind, not of arithmetic.** The measured rate is **26 of 448 entities, about 1 in 17**, and in `## Feature design` **21 of 117, about 1 in 5.6**. **Read that as the rate over the units extracted so far, not as the corpus rate.** It comes from 8 units chosen for the AC-14 coverage set, not a random cut of the corpus's 188 sections, and `## Feature design`'s figure rests on a single unit. What it is enough to establish is that the struck sentence was wrong by an order of magnitude and wrong in kind; what it is not enough to establish is where the rate settles across the whole corpus. The Follow-up below owes that re-calibration. The 99.4% figure was honest about what it measured and was read as measuring something else: it comes from `locate_line()`'s own calibration over the corpus's 316 real acceptance criteria, **mutated synthetically** the way extraction was expected to mutate them (a rationale clause dropped, wrapping collapsed, inline markup stripped), each scored against its own unit. Real model output mutates a span harder than that model of it does, so a threshold calibrated on synthetic mutations overstates its hit rate on live output by an order of magnitude. **Never quote a locate rate measured on synthetic spans as the rate on extracted ones.** The difference matters because it changes the verdict: 1 in 170 is a rounding error worth writing a caveat about, which is all the struck sentence did; 1 in 17, and nearly 1 in 5 in the largest and most varied unit kind in the corpus, is a hole, which is why AC-11(d) now routes those entities to review instead of letting them accept on a count.

**Neutral**:

- The vocabulary is now larger than HANDOFF's: eight entity types against four, seven relationship types against five. The prompt and its few shot examples must be rewritten from the enums rather than reused as they are.
- Three node kinds mean three uniqueness constraints and three write paths in the loader.
- `rationale` spans are stored on the node as a list, so nodes are wider than the tested pipeline's output.
- **Added 2026-09-23, a warning about the evidence this spec cites.** Every agreement number measured so far, in [experiment 0001](../../../experiments/0001-ac14-type-stability/README.md), in [experiment 0002](../../../experiments/0002-effort-low-fidelity/README.md), and in the 21 call run, was produced under the **old** rule: set comparison with flags inside the signature.

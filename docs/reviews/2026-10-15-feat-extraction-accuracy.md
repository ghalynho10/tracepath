## Minor

### 🟡 F1. A packet head the parser does not recognise bleeds its reason into the item before it, `src/tracepath/measure.py:340`
**Problem**: `parse_rulings()` resets `current` only when `_ANY_HEAD` matches a line. A head the engineer edited into another shape (for example `- [X] agree · ...` with a capital X, or a separator other than `·`) matches neither regex, so `current` stays on the previous item and the next `  - reason:` line replaces that previous item's reason. The reason carries the `gap:bundled-ac` tag that `flip_bundled()` reads and the `knowledge` keyword that `arm_score()` counts, so a flip or a knowledge count can silently move to the wrong item. The unrecognised item itself does show up: it is absent from `rulings` and listed under `unruled` in the result, which counts against the gate, so the failure is not fully silent. In the committed packet every one of the 22 heads matches, so the recorded result is unaffected (verified by grep over `data/stage-one-packet.md` and by the re-scoring test).
**Why it matters**: The reflex says to guard what can produce a misleading result. A stage two packet or a later step's packet ruled by hand is exactly where a head gets edited, and a reason moving one item up can turn an agree into a disagree on the wrong row.
**Suggested fix**: Treat any line that starts `- [` as a head: reset `current` and refuse the line (raise `RulingsRefused`) when it does not match `_RULED_HEAD` or the unruled form, instead of only when it starts `- [x]`. Add the capital X case to the parser's tests.

### 🟡 F2. The cached prefix figure drifted from what AC-31g and the build plan say, `src/tracepath/extract/cost.py:37` and `docs/specs/0007-extraction-accuracy/index.md:105,182,218`
**Problem**: AC-31g says the cached prefix in `cost.py` stays 57,494 "until a paid call on `claude-sonnet-5-5` reports its cache write", and build plan step 6 says a difference "is recorded in this spec before the estimate uses it". The first paid call reported 57,493 (experiment 0012 README, Configuration). The engineer chose to keep 57,494, which is a reasonable call at $0.0000039 per call, but it is recorded only in the experiment README: the spec's Follow up item on line 218 is still unticked, AC-31g is not amended, and `estimate_lines()` (`cost.py:272`) still prints "57,494 tokens, as billed (experiment 0008)", which is no longer what the current model bills.
**Why it matters**: The spec is the record of decisions, and this one says the figure moves or the spec says why it did not. A later reader of `cost.py` or the estimate line will believe the prefix was measured on the current model.
**Suggested fix**: Amend AC-31g in the spec with the measured 57,493 and the decision to keep 57,494 (one line), tick the Follow up, and change the estimate line to name the model the prefix was billed on.

### 🟡 F3. The AC-7d test proves the helper, not the command, `tests/test_code_pass_commands.py:207`
**Problem**: AC-7d claims "the routing that `eval` and `trace --eval` score and explain is the routing with the pass applied". `test_ac_7d_the_scoring_routes_with_the_pass` asserts `_committed(ROOT, SNAPSHOT, COMMIT, True).results == apply_code_pass(committed_units(...))`. That proves `_committed` applies the pass when told to; it does not run `eval --code-pass` or `trace --eval N --code-pass` and read what they print, so the wiring in `cli.py:580` and `cli.py:651` (passing `code_pass` through) is covered only by reading the code. This is the pattern the one claim per criterion reflex warns about: a test tagged AC-7d reads as covering it.
**Why it matters**: A later edit that drops the `code_pass` argument from one of the two call sites would keep this test green while `eval --code-pass` scores the default routing against a graph loaded with the pass.
**Suggested fix**: Make it an integration test: load a small root with `--code-pass`, run `eval --code-pass` and `trace --eval N --code-pass`, and assert a released entity is reported accepted (or compare the printed report to the pass routing). Or at least assert on the `_committed` call in both commands through a monkeypatched `_committed`.

Two things I checked that could have changed the set and did not:

- The parse of AC-9 against the corpus. No `## Requirements` bullet in any record is wholly struck (`- ~~**AC-`), none opens `~~` after the colon except the one the report counts in 0009, and none is indented. The top level `- **AC-` bullets the parse refuses are prose bullets in reviews and session notes plus criteria of the form `- **AC-N** (added date): ...` in records 0009 (one, AC-24), 0019 and 0021. For the chosen units the report rows on the current code read: 0009 decided 22, released 7, unparsed 1; 0013 decided 12 of 12 parsed, released 3; 0015 decided 17 of 17, released 8. So 0013's shortfall (3 released, the reason stage one is inconclusive) comes from only 3 of its 12 criteria being held by the flag alone, not from the parse refusing bullets. A relaxed parse that accepted a parenthetical before the colon would be a spec change to AC-9, not a fix, and would add at most one id to 0009's pool.
- `_flag_alone_releasable()` reads every run's entity by canonical id. A verbatim id with struck and unstruck text takes a derived canonical id for the struck twin (spec 0002 AC-5), so it never collides with `record/AC-N`, and `_settles()` already refuses an id with two verbatim claimants in a run. So no entity is released that the spec would hold, and none is held that it would release.
